## 一、结论摘要

第二优先级已完成。项目现在可以从干净克隆开始，使用 Git 中的两份真实项目 PDF，在不提交模型权重、提取产物或向量索引的前提下，完成以下闭环：

```text
安装锁定依赖
→ 准备并校验四个本地模型
→ 校验两份 Git PDF
→ 从 PDF 重建提取产物和索引
→ 通过真实 STDIO 会话发现 MCP 工具并读取知识库状态
→ 运行完整测试、证据门禁和运行时基准
```

2026-08-15 的完整演练在 Windows 11、Python 3.12.13、uv 0.11.14 环境中通过，共重建 2 份文档、393 页、731 个 chunk，总耗时 1519.25 秒。发布清单、PDF 与模型哈希、MCP 连通性、96 项测试、两组证据门禁和运行时基准均通过。

本阶段解决的是“别人能否从零安装、重建、测试和启动项目”。它没有调整切块、BM25、向量召回、RRF、reranker 或证据阈值，也不能替代仍待授权的第一优先级真实答案级评测。

## 二、调优前的问题

| 问题 | 影响 |
| --- | --- |
| `data/` 整体被 Git 忽略 | 干净克隆缺少实际复现输入，必须依赖本机已有 PDF |
| 安装与测试入口未完全锁定 | `unittest discover` 不能收集全部 pytest 风格测试，测试工具版本也未进入锁文件 |
| 模型准备未覆盖完整链路 | Embedding、reranker 与 OCR 模型缺少统一、可校验的准备流程 |
| MCP 配置包含本机绝对路径 | 换机器或换工作目录后不能直接复用 |
| 复现计划未验证真实 MCP 会话 | 只能证明脚本和测试运行，不能证明客户端可以发现工具并读取知识库状态 |
| 复现输入与生成资产边界不清晰 | 容易错误提交大模型、OCR 产物或向量索引，或者把本机生成物当成复现前置条件 |

## 三、实施内容

### 3.1 固定仓库输入

`.gitignore` 调整为只允许跟踪 `data/*.pdf`，并通过提交 `04aafd5` 纳入两份真实项目输入：

| 文件 | 大小 | SHA-256 |
| --- | ---: | --- |
| `data/南京邮电大学学生手册（2023版）+.pdf` | 2,444,739 字节 | `95718365ef1ad87df9e4bbd692bada066a4176328f19983534cf73d61682fc30` |
| `data/奖学金细则.pdf` | 4,286,200 字节 | `d4277dffe694e105ba6b5cfc9551ecd84b37d5a4068b02e3e63395719165a161` |

`models/`、`storage/`、缓存和详细运行报告继续保持 Git 忽略。复现时必须从上述 PDF 重新生成提取产物与索引，不能借用仓库外的 PDF 或预生成索引。

### 3.2 锁定依赖与模型输入

- 使用 `uv sync --frozen --all-groups` 按 `uv.lock` 安装依赖；
- 将 `pytest==9.1.1` 纳入 dev 依赖，完整测试入口统一为 `python -m pytest -q`；
- `src/prepare_model.py` 统一支持 Embedding、reranker 和 OCR 模型准备；
- 使用 `RAG_ASSET_ROOT` 支持在独立资产目录中完成无污染复现；
- 对四个完整模型目录计算树级 SHA-256，覆盖权重、配置和 tokenizer，而不是只检查目录存在。

固定模型及目录哈希如下：

| 用途 | 模型 | 目录 SHA-256 |
| --- | --- | --- |
| Embedding | `BAAI/bge-base-zh-v1.5` | `9aeef0fb07d1df4047371c11bf4f54efaac7ecbc1c87c7cc3900625ad8ec4c3d` |
| reranker | `BAAI/bge-reranker-base` | `2148550b82e254e00bc6886bdcedb689661002652c218ea0adf5d12f26553968` |
| OCR 检测 | `PP-OCRv6_medium_det` | `0f4b1f22be778b1abe94b2b2d930ce5fae3c4ff8a607efe6ccdc40740c07f22f` |
| OCR 识别 | `PP-OCRv6_medium_rec` | `d70df33cf7dbe4348ea3e182f35b3226a4675d292c96a3413018d183bcc861e0` |

### 3.3 统一 PDF 重建入口

复现计划固定调用 `src/ingest.py`，从仓库内两份 PDF 重建全部提取产物和索引。扫描 PDF 的发布复现固定使用 160 DPI，以控制 CPU 环境下的执行时间；日常高质量导入仍可使用默认 300 DPI。

OCR 引擎创建逻辑被提取为共享入口，使模型准备与扫描件提取使用同一组检测、识别模型及参数，减少“下载模型”和“实际运行模型”不一致的风险。

### 3.4 提供可移植 MCP 配置与真实会话验证

项目级 `.codex/config.toml` 从本机 Python 绝对路径改为：

```toml
command = "uv"
args = ["run", "--frozen", "python", "src/mcp_server.py"]
cwd = "."
```

新增 `evaluation/verify_mcp.py`，通过真实 STDIO 会话完成：

1. MCP 初始化；
2. 工具发现；
3. 校验工具集合为 `knowledge_base_status` 和 `search_knowledge_base`；
4. 调用 `knowledge_base_status`；
5. 校验索引包含 chunk。

该验证不调用外部大模型，也不生成示例对话。

### 3.5 收口单一复现与证据记录

`evaluation/reproduction_plan.json` 统一描述前置哈希与六个执行步骤；`evaluation/reproduce_release.py` 提供只读预检和完整执行两种模式。`evaluation/release_manifest.json` 冻结 84 个发布输入，`evaluation/reproduction_result.json` 保存精简验收结果及被忽略详细报告的 SHA-256。

详细命令和从干净克隆开始的操作说明已写入项目 [README](../README.md)。

## 七、边界与剩余风险

- 完整复现目前只在上述 Windows 11 环境验收；Linux、macOS、GPU 和不同 CPU 的兼容性及耗时尚未形成独立记录。
- 模型目录哈希可以发现版本漂移，但首次准备模型仍依赖下载源和网络可用性。
- 160 DPI 是当前 CPU 发布复现的成本折中。此前 300 DPI 演练运行 30 分钟仅完成 23/30 个 OCR 页面，原子事务正确保留了旧索引；300 DPI 仍属于高成本模式。
- 详细生成报告和索引继续被 Git 忽略，仓库只保存精简结果和详细产物哈希；长期审计时应妥善保管外部详细报告。
- 347 条启发式警告不阻断本次复现，但在扩充语料或开展答案失败分析时仍应抽检。
- 本报告不声明最终答案正确率、引用准确率或拒答遵守率；这些指标仍属于第一优先级真实答案评测。
