# RAG MCP 后续优化计划

| 项目 | 内容 |
| --- | --- |
| 文档日期 | 2026-08-14 |
| 当前定位 | 基于 MCP 的本地校园 PDF 检索与证据服务 |
| 优化原则 | 先完成答案评测和项目复现，再根据失败案例定向优化 |

## 执行进度（同步于 2026-08-14）

| 优先级 | 当前状态 | 已完成 / 未完成边界 |
| --- | --- | --- |
| 第一优先级 | **进行中** | 本地评测基础设施已完成并通过测试；真实 12 题答案生成、人工复核和最终指标仍等待本地校园 PDF 证据的数据外发授权 |
| 第二优先级 | **未启动** | 仓库直接携带当前项目用于复现的两份 PDF；干净克隆后按 README 下载模型，并从这些 PDF 重新生成提取产物和索引，不准备额外样例或演示资产 |
| 第三优先级 | **未启动** | 尚未根据本轮答案级失败案例修改检索、切块、拒答或模型参数 |
| 第四优先级 | **未启动** | 现有预热、缓存和基准属于计划前能力；本轮没有开展新的性能优化验收 |

第一优先级的详细实施状态见[《2026-08-14 第一优先级答案级评测实施报告》](./2026-08-14-第一优先级答案级评测实施报告.md)。在真实评测与人工复核完成前，不把“运行器已实现”写成“答案评测已验收”。

## 当前结论

现有系统已经覆盖 PDF 导入、原生与扫描件提取、OCR、切分、BM25 与向量混合召回、RRF 融合、Cross-Encoder 重排、证据充分性判断、来源追踪、MCP 工具暴露和检索评测。

当前不需要为了形式上的“完整”增加 HTTP API。自然语言答案由 Codex 或其他 MCP 客户端中的大模型生成，MCP Server 负责提供检索结果和证据约束。下一阶段的重点不是继续广泛搜索检索参数，而是证明最终答案是否正确、引用是否可靠，以及项目能否在干净环境中复现。

## 第一优先级：完成答案级评测

> 当前状态：进行中。固定配置、问题集、真实客户端运行器和评估器已完成；正式运行与人工复核待授权。

### 目标

验证真实 MCP 客户端能否遵守工具 description，根据检索证据生成正确、完整且可追溯的答案，并在证据不足时可靠拒答。

### 工作内容

1. 固定一次评测使用的 MCP 客户端、模型名称和 description/Prompt 版本。
2. 准备固定问题集，至少覆盖普通文本、表格、扫描 PDF、知识库外问题、错误学校和时效性问题。
3. 通过真实 MCP 客户端生成答案，保存以下信息：
   - 原始问题；
   - `evidence_sufficient`、`confidence` 和 `reason`；
   - 检索结果和 chunk ID；
   - 最终答案或拒答；
   - 答案引用的 chunk ID；
   - 客户端、模型和 Prompt 版本。
4. 使用现有答案评估器进行自动诊断，并人工复核正确性、完整性和引用支持情况。

### 核心指标

- 答案正确率；
- 答案完整性；
- 引用准确率与引用召回率；
- 答案是否被引用证据支持；
- 错误回答率；
- 错误拒答率；
- `evidence_sufficient=false` 时的拒答遵守率；
- 是否出现使用模型记忆补充或猜测的情况。

### 验收标准

- `evidence_sufficient=true` 时，答案只包含证据能够支持的事实，并引用 `source_file`、`page` 和 `chunk_id`。
- `evidence_sufficient=false` 时，客户端明确拒答，不根据常识或模型记忆补充结论。
- 评测结果能够区分检索错误、证据判断错误和生成错误，而不是只报告一个总分。

## 第二优先级：实现干净环境复现

> 当前状态：未启动。按用户要求，在第一优先级完成前不实施本节。

### 目标

让使用者从干净仓库开始，直接使用 Git 中已跟踪的两份项目 PDF，在不提交大模型文件或生成后向量索引的前提下，按照 README 完成依赖安装、模型准备、PDF 提取、索引重建、测试和 MCP 启动。

### 工作内容

1. 不另外准备两到三份小型样例 PDF；将当前项目实际使用的 `data/奖学金细则.pdf` 和 `data/南京邮电大学学生手册（2023版）+.pdf` 作为复现输入直接纳入 Git。
2. 补充从干净克隆安装 Python/uv 依赖的命令，并列出 Embedding、reranker、OCR 检测和 OCR 识别模型的固定版本。
3. 对体积较大的模型，只在 README 提供官方或可信下载地址、下载命令、目标目录和必要的校验方式，不把模型权重提交到 Git。
4. 使用当前统一的 `src/ingest.py` 从仓库内两份 PDF 完成类型识别、提取、切块、向量生成和索引构建；README 给出可直接复制的 dry-run 与正式运行命令。
5. 对生成后的 `storage/`、Embedding 向量和 BM25 索引，只记录生成脚本、配置、schema、文档/chunk 数和可选哈希，不上传整个向量库或索引目录。
6. 补充 MCP Server 启动命令和一个最小客户端配置，使干净环境能够完成工具发现、`knowledge_base_status` 与自动化测试；不额外准备标准问题、示例对话、录屏或展示型 Demo。
7. 记录操作系统、Python/uv 版本、模型版本、输入 PDF 哈希、关键命令、索引摘要和复现结果；失败时能够指出缺少的依赖、模型或仓库输入 PDF。

### 大文件与本地数据策略

- Git 保存源码、配置、脚本、测试、文档、必要的小型评测元数据，以及复现索引所必需的两份 `data/*.pdf` 输入文件。
- `models/`、`storage/`、运行报告和缓存继续由 `.gitignore` 排除；`data/` 只允许 PDF 被跟踪，其他临时文件仍忽略。
- 模型通过 README 中的地址或命令下载；若工具支持，记录版本或 SHA-256，避免下载到不确定版本。
- 向量库和提取产物必须能由仓库脚本从已跟踪的 PDF 重建，不把生成物作为复现前置条件。
- 复现验证关注“项目能够安装、重建、测试和启动”，不增加与功能无关的演示材料。

### 验收标准

完整流程可以从以下初始状态运行：

```text
干净克隆仓库
→ 安装依赖
→ 按 README 下载或准备固定版本模型
→ 校验仓库内两份输入 PDF
→ 运行 ingest，从 PDF 重新生成提取产物和向量索引
→ 启动 MCP Server
→ MCP 客户端发现工具并读取知识库状态
→ 完整自动化测试通过，且生成资产可再次从零重建
```

验收要求仓库包含两份输入 PDF，但不提交模型权重、提取产物或向量库，也不要求制作额外的 Demo、示例对话或录屏。

## 第三优先级：根据失败案例定向优化

> 当前状态：未启动。没有答案级失败证据前不进行本节优化。

### 目标

只优化答案级评测和独立检索评测已经证明存在的问题，避免无目标地调整 chunk、RRF 权重、Top-K 或模型。

### 优化方向

#### 表格问题

- 检查表头是否在每个相关 chunk 中保留；
- 检查字段和值的关系是否被切分破坏；
- 检查跨页表格、宽表格和缺少表头的表格；
- 分析错误来自候选召回还是 reranker 排序。

#### 扫描 PDF

- 检查 OCR 阅读顺序异常；
- 检查短文本、重复行和跨页标题；
- 对低置信度页面保留人工复核入口；
- 分别报告原生 PDF 与扫描 PDF 的指标。

#### 拒答策略

- 分别统计错误回答和错误拒答；
- 检查知识库外问题、错误学校、错误前提和时效性问题；
- 避免只依赖单一 reranker 分数阈值；
- 继续利用分差、检索通道一致性、词面覆盖、证据来源和 OCR 质量等信号。

#### 评测隔离

- 只使用 development 集分析和调优；
- 调优完成后创建新的未见 locked 集；
- 不使用已经查看过的 locked 结果继续调整配置；
- 每轮记录数据、代码、配置和模型版本。

### 验收标准

每项代码或配置修改都必须对应一个可复现的失败案例，并在 development 集上证明改善，在新的 locked 集上完成非回归验证。

## 第四优先级：性能与运行体验

> 当前状态：未启动。已有性能基准、预热和缓存保持不变，不视为本计划的新实施结果。

### 目标

在不明显降低检索质量的前提下改善 MCP 长进程的启动和查询体验。

### 可选工作

- 保持服务启动时预热索引、Embedding 模型和 reranker；
- 展示冷启动、非缓存查询和缓存查询的独立耗时；
- 保留查询缓存和索引变更后的缓存失效；
- 记录检索、重排和证据判断的分阶段耗时；
- 在有明确性能目标后，再评估更轻量的 reranker 或推理格式；
- 保持 README 中的 MCP 配置和启动说明与代码一致，不新增展示型 Demo 资产。

### 验收标准

- 实际运行使用预热后的 MCP 长进程，不为每个问题重复加载模型；
- 性能优化必须同时报告质量指标，不能只比较延迟；
- 若性能方案导致关键 Recall、MRR、引用或拒答指标下降，则不采用。

## 当前不建议进行的工作

- 不为了展示技术栈额外增加 HTTP API；
- 不强行引入 LangChain、LlamaIndex 等框架；
- 不为当前数据规模更换复杂向量数据库；
- 不在答案级评测完成前进行大范围参数搜索；
- 不使用已查看的 locked 集反复调参；
- 不在没有失败案例和指标依据时微调 Embedding 或 reranker 模型。
- 除两份必要的项目输入 PDF 外，不为了复现上传额外数据、大模型权重、提取产物或整个向量库；
- 不额外制作与安装、重建、测试和启动无关的 Demo、示例对话或录屏。

## 推荐执行顺序

| 阶段 | 当前状态 | 主要产物 | 完成标志 |
| --- | --- | --- | --- |
| 1. 答案评测 | 进行中 | 固定问题集、真实答案预测、答案级报告 | 能量化正确、引用和拒答表现 |
| 2. 项目复现 | 未启动 | 两份已跟踪输入 PDF、模型下载说明、索引重建命令、客户端配置、复现记录 | 不携带模型和生成索引时，干净环境仍可完成安装、重建、测试和 MCP 启动 |
| 3. 定向优化 | 未启动 | 失败案例、实验记录、新 locked 集结果 | 改善明确且无关键指标回退 |
| 4. 性能与运行体验 | 未启动 | 性能报告和运行参数说明 | 在目标硬件上满足质量与延迟门槛 |

项目后续主线应保持为：

```text
完成 MCP 检索服务
→ 验证最终答案
→ 实现干净环境复现
→ 根据失败案例定向优化
→ 最后改善性能和运行体验
```
