## 5. 问题与解决方案

### 5.1 P0-1：无答案问题仍会返回无关证据

#### 原始现象与证据

当前 `search` 始终返回候选，MCP 结果没有 `evidence_sufficient` 或等价字段。真实查询“学校附近明天会不会下雨”时，系统仍返回安全管理、宿舍和考试规定等无关片段。

v1 开发集校准的单一 raw reranker 阈值在旧锁定集上把错误回答率压到 5%，但错误拒答率达到 35%，扫描 PDF 的错误拒答率达到 50%。v2 修改了最终排序分数的定义，最终 `score` 现在包含按排名归一化和检索先验，更不能直接沿用 v1 阈值。v2 的 40 条验收集全部是可回答问题，不能证明拒答能力已经改善。

#### 解决方案

1. 不复用 v1 的单一阈值，也不对 v2 最终排序 `score` 直接设阈值。
2. 在开发数据上构建证据充分性特征，至少包括 raw reranker 分数、Top 1/Top 2 分差、BM25/向量通道一致性、前几名证据的文档和页面一致性、查询类型、OCR 质量和证据覆盖情况。
3. 新增与 v2 验收集文档隔离的无答案数据，覆盖知识库外、时效信息、错误前提、错误实体或学校四类问题。
4. 在 MCP 响应中增加结构化判断，例如 `evidence_sufficient`、`confidence` 和 `reason`；证据不足时允许返回调试候选，但明确要求调用方不得据此作答。
5. 分别报告错误回答率和错误拒答率，不能只报告一个综合准确率。

#### 验收标准

- 在新的未见测试集上，无答案错误回答率不高于 5%。
- 错误拒答率显著低于旧基线 35%，并单独报告原生/扫描 PDF 结果。
- 四类无答案问题均有足够样本，且没有与开发文档发生哈希重叠。
- MCP 客户端能够通过结构化字段稳定识别“证据不足”。

### 5.2 P0-2：缺少端到端答案质量评测

#### 原始现象与证据

原始状态只有 `evaluation/evaluate_answers.py`、答案预测模板、gold answer、required facts 和精确 chunk qrel，`system_answer_score` 为空。2026-08-14 的第一优先级已进一步新增固定 12 题、`answer-eval-v1` Prompt/Schema、真实 Codex CLI + STDIO MCP 运行器和更完整的答案/引用/拒答指标，但正式预测仍未生成。Recall、MRR 和 NDCG 只能证明证据排名；在真实运行和人工复核前，仍不能声明上层模型回答正确、完整并受到引用支持。

#### 解决方案

1. 明确实际使用的 MCP 客户端、上层模型、提示词和最大证据数量，并固定版本。
2. 通过真实 MCP 调用生成回答或拒答，同时记录实际引用的 chunk ID。
3. 使用 `evaluation/evaluate_answers.py` 计算必需事实覆盖和引用精确率/召回率。
4. 对正确性、完整性、引用支持度进行人工复核；自动字符匹配只作为诊断。
5. 配置确定后，只在新的未见测试集上运行一次最终评测，避免根据测试结果继续调参。

#### 验收标准

- 所有评测问题都有回答或明确拒答，并保存引用 chunk ID。
- 可回答问题完成人工正确性、完整性和引用支持度复核。
- 无答案问题报告幻觉回答率和正确拒答率。
- 报告记录模型、提示词、检索配置、数据集哈希和运行时间。

### 5.3 P0-3：v2 冻结与评测链路不可完整审计和复现

#### 原始现象与证据

当前工作区缺少 v1/v2 的生成索引和详细评测报告，例如：

- `storage/evaluation_splits/development/index/metadata.json`
- `storage/evaluation_splits/locked_test/index/metadata.json`
- v2 验收索引及 `evaluation/reports/acceptance-v2-final.json`
- `evaluation/reports/expanded-development.json`
- `evaluation/reports/expanded-locked.json`

此外存在三项一致性问题：

1. `evaluation/validate_dataset.py` 默认仍校验 `evaluation/config_freeze.json`，没有完整接入 v2 冻结文件和 v2 验收集。
2. 运行旧校验时，当前 v2 检索代码必然与 v1 冻结哈希不一致。
3. `evaluation/config_freeze_v2.json` 中多数 `frozen_file_sha256` 与当前同一提交中的代码内容不匹配，且并非仅由 LF/CRLF 换行差异导致。

因此，v2 冻结文件记录的指标可以作为本轮历史结果，但当前尚不能从干净环境自动证明“这些结果确实由当前提交和声明的输入生成”。

#### 解决方案

1. 为 v2 单独实现或扩展冻结校验器，校验代码、模型、数据集、输入 PDF、提取产物、索引和报告。
2. 对文本文件统一使用可移植的换行归一化哈希，并为二进制文件保留原始字节哈希。
3. 在冻结参数后立即生成冻结清单；冻结后任何代码变化必须开启新的评测周期，而不是覆盖旧清单。
4. 提供单一入口依次完成 PDF 校验、提取、索引构建、qrel 校验、策略对比和报告生成。
5. 在清理后的新 worktree 中演练重建，确认命令不依赖旧工作区中的隐式文件。
6. 生成内容继续忽略 Git 时，至少保存获取说明、哈希、目录约定和重建命令；关键小型报告可以考虑纳入版本控制。

#### 验收标准

- v2 冻结校验对当前声明的冻结提交返回成功。
- 修改任一冻结代码、标签、模型或输入文件后，校验能够失败并指出具体对象。
- 干净环境可以重新生成 v2 索引和最终报告。
- 重建报告的输入哈希和核心指标与冻结记录一致，或对确定性的允许误差作出书面定义。

### 5.4 P1-1：表格与精排优化仍需扩大验证范围

#### 已完成进展

v2 已实现：

- 表格按行切块并重复标题和表头；
- 为 BM25 生成字段—值形式的表格检索文本，超宽表格采用无损 Markdown 回退；
- Embedding 和 reranker 继续使用原始证据文本；
- 对表格查询和高置信度 Hybrid Top 5 候选提供保护；
- 新增基线/优化策略公平对比工具和 40 条精确 qrel 验收集。

这些改动使 v2 在验收集上保持 Recall@5 1.0，并改善 Recall@1、MRR@5 和 NDCG@5。旧版“表格 Recall@5 0.80”的结论不再代表当前策略。

#### 剩余风险

- 验收集只有 2 份新文档和 40 条问题，虽然一半是表格题，但覆盖规模有限。
- v2 Recall@3 从 1.0 降到 0.975，说明 Top 3 内仍存在排序权衡。
- 当前缺少可重跑的详细报告，无法直接查看每类表格和每种 PDF 的失败明细。

#### 解决方案

1. 保持当前 v2 参数冻结，不用本轮验收集继续调参。
2. 从新的未见文档建立下一轮困难集，覆盖跨页表格、多级表头、合并单元格、裸数字、相似实体和扫描退化。
3. 对所有失败样本归类为提取失败、切块失败、候选召回失败、Top 3 错排或 Top 5 错排。
4. 同时检查 Recall@1、Recall@3、Recall@5、MRR、NDCG、表格类别和 PDF 类型。

#### 验收标准

- 新一轮表格 Recall@5 不低于 1.0 或预先声明的发布门槛。
- Recall@1/MRR 的提升不以明显降低 Recall@3 为代价。
- 原生、扫描、普通文本和表格题分别报告指标。

### 5.5 P1-2：CPU 查询延迟较高

#### 原始现象与证据

本机首次查询约 12 秒，热查询约 2.9 秒。v2 开发集记录的 reranker 平均查询耗时约 2.63 秒，P95 约 3.66 秒。已有实验表明直接把候选数从 20 降至 10、15 或 16 会造成质量回退，因此不能简单用减少候选换速度。

#### 解决方案

1. MCP 服务启动时预加载或预热 Embedding 和 reranker，把冷启动移到服务启动阶段。
2. 在保持 20 个候选的前提下评估 ONNX、量化或 GPU 推理。
3. 为相同查询和固定索引版本增加小型缓存，索引变化后必须失效。
4. 分别记录模型加载、查询 Embedding、BM25、向量检索、融合和 reranker 时间。
5. 先确定目标硬件和并发量，再设置性能门槛。

#### 验收标准

- 明确目标硬件上的冷启动、热查询 P50/P95 和并发目标。
- 性能优化不低于 v2 冻结质量指标。
- 缓存不会跨索引版本返回旧结果。

### 5.6 P1-3：README 和当前 v2 行为不一致

#### 原始现象与证据

README 仍主要描述 v1 的 `config_freeze.json`、80 条可回答加 20 条无答案锁定集、旧 reranker Recall@5 回退和旧表格候选召回问题，没有介绍 schema 4、表格检索文本、Top 5 保护、`config_freeze_v2.json`、v2 验收集和策略对比工具。

#### 解决方案

- 将 v1 指标明确标记为历史评测。
- 增加 v2 当前配置、验收集、运行命令和已知限制。
- 在修复 P0-3 后，README 只提供实际可在干净环境执行成功的命令。
- 明确最终答案由 MCP 客户端生成，仓库当前不声称具备答案正确率。

#### 验收标准

- README 中的分支、schema、配置文件、数据规模和指标与当前代码一致。
- 文档中的所有验证命令在声明的前置条件下可执行成功。

### 5.7 P2-1：实际运行规模仍较小

#### 原始现象与证据

当前日常运行索引只有 2 份 PDF 和 731 个 chunk。v2 冻结记录中的验收索引为 8 份文档、1511 个 chunk，但对应索引当前不在工作区；现有证据仍不足以证明几十或几百份文档下的构建时间、内存、查询延迟和跨文档混淆情况。

#### 解决方案与验收标准

- 建立 10、50、100 份文档的分级规模测试。
- 记录提取耗时、索引构建耗时、索引大小、峰值内存和查询 P50/P95。
- 增加同名制度、不同年份、废止版本和相似实体冲突测试。
- 明确支持的最大文档数、目标硬件以及可接受的性能和质量门槛。

### 5.8 P2-2：文档导入和索引更新依赖人工流程

#### 现象与证据

当前需要人工判断 PDF 类型，分别运行原生或扫描提取命令，再构建索引。索引能够通过源摘要判断是否复用，但缺少面向普通使用者的统一导入、质量检查和失败回滚入口。

#### 解决方案与验收标准

- 提供统一 `ingest` 流程：识别类型、提取、质量检查、构建索引并输出变更摘要。
- 构建前报告新增、修改、删除和失败文档。
- 在临时目录构建新索引，全部成功后再切换；失败时旧索引保持可用。
- 状态接口显示索引版本、生成时间、文档列表和待更新状态。

### 5.9 P2-3：检索层与完整问答产品边界不够明确

#### 现象与证据

当前 CLI/MCP 返回证据片段，不包含答案生成。这对于由 Codex 或其他 MCP 客户端生成答案的架构是合理的，但不能把检索 Recall 直接称为最终答案正确率。

#### 解决方案与验收标准

- 如果定位为 MCP 检索工具，保持答案生成在客户端，补充证据充分性字段和端到端集成评测。
- 如果定位为独立问答产品，新增答案生成层、强制 chunk 引用并在证据不足时拒答。
- README、演示行为和评测口径必须对“谁生成答案”保持一致。

### 5.10 P2-4：本地演示尚未被 Git 跟踪

#### 现象与证据

`docs/` 已从 `.gitignore` 移出并纳入版本控制，问题清单、调优路线和实施报告现在具有共同、可审计的来源。`slides/` 仍被忽略，不会随分支或克隆携带。

#### 解决方案与验收标准

- 当前 Markdown 文档的验收标准已满足：干净克隆能够获得同一版本的问题清单和路线总结。
- 如果 HTML 演示需要作为正式交付物，应移除 `slides/` 忽略规则、核对内容后显式提交。
- 在此之前，索引中继续明确 HTML 演示只存在于本地。

## 6. 推荐实施顺序

### 第一阶段：修复评测可信度

1. 修复 v2 冻结哈希和校验入口。
2. 建立可从干净 worktree 重建索引和报告的流程。
3. 更新 README，使其反映 v2，而不是继续把 v1 当作当前状态。

### 第二阶段：补齐真实用户质量闭环

1. 建立 v2 无答案开发集和未见测试集。
2. 实现结构化证据充分性判断。
3. 固定 MCP 客户端、模型和提示词，完成端到端答案评测。

### 第三阶段：性能和交付

1. 预热或加速本地模型。
2. 增加统一 ingest 和安全索引切换。
3. 建立规模化与多版本文档测试。

## 7. 当前不建议的做法

- 不建议继续使用本轮 v2 验收集调参；它已经用于最终验收，应进入历史冻结状态。
- 不建议直接复用 v1 拒答阈值，也不建议对 v2 最终排序 `score` 设置简单阈值。
- 不建议为降低延迟直接减少候选数量；已有实验显示会造成召回或排序回退。
- 不建议立即更换 Embedding 或 reranker；v2 当前主要缺口是拒答、端到端评测和可复现性。
- 不建议继续引用旧版“表格 Recall@5 0.80”作为当前系统指标。
- 不建议只看 Recall@1 或 Recall@5；还需同时检查 Recall@3、MRR、NDCG、PDF 类型、表格类别和无答案行为。

## 8. 已确认与仍待确认事项

本轮已经确认：

仍需用户或发布负责人确认：
