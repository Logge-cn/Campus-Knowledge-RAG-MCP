## 一、实施目标

本次实施用于验证真实 MCP 客户端是否能够：

1. 根据工具 description 主动调用本地校园 PDF 知识库；
2. 仅在 `evidence_sufficient=true` 时依据检索证据作答；
3. 在 `evidence_sufficient=false` 时明确拒答，不使用模型记忆、常识或猜测补充结论；
4. 在答案中同时引用 `source_file`、`page` 和 `chunk_id`；
5. 将失败归因到检索、证据判断或答案生成阶段。

本次没有创建 worktree，也没有实施后续计划中的项目复现、定向检索优化和性能改进。

## 二、冻结的评测配置

| 配置项 | 固定值 |
| --- | --- |
| MCP 客户端 | 当前 Codex 会话创建的逐题子 agent |
| 客户端版本 | 由当前 Codex 宿主管理，不再嵌套启动 CLI |
| 模型 | `gpt-5.6-sol` |
| Prompt 版本 | `answer-eval-v1` |
| 工具 description 版本 | `answer-eval-v1` |
| 每题最大证据数量 | Top 5 |
| MCP 传输方式 | 本地 STDIO |
| 上下文隔离 | 每题一个 `fork_turns=none` 的全新子 agent，最多 3 个并发 |
| 客户端权限 | 子 agent 只允许一次 `search_knowledge_base` 调用和一次独立结果文件写入 |
| 服务启动方式 | 复用当前 Codex 宿主已连接的项目级 MCP；不改变检索配置和服务默认行为 |

Prompt 只向客户端提供问题 ID 和原始问题，不提供 gold answer、required facts 或相关 chunk ID，避免答案泄漏。

## 四、隔离子 agent 评测链路

新增 `evaluation/run_answer_evaluation.py`，执行流程如下：

```text
读取固定问题集与版本化 Prompt
→ 为每题生成不含 gold 数据的独立任务
→ 以最多 3 个并发槽创建 fork_turns=none 的全新 Codex 子 agent
→ 每个子 agent 调用一次 search_knowledge_base(limit=5)
→ 每个子 agent 写入唯一的 case-results/<id>.json
→ Runner 逐题校验查询、参数、完整 MCP 结果、拒答和引用
→ 按数据集顺序合并最终答案、拒答和引用
→ 生成 predictions.json、manifest.json 和自动诊断报告
```

每次运行会保存：

- 原始问题；
- `evidence_sufficient`、`confidence` 和 `reason`；
- 完整检索结果及 chunk ID；
- 最终答案或明确拒答；
- 答案实际引用的 `source_file`、`page` 和 `chunk_id`；
- 客户端、隔离模式、模型、Prompt、description、数据集和代码版本信息；
- 12 个互不争用的逐题结果文件及其协议版本。

Runner 不再启动 `codex exec`，只负责准备、校验、汇总和报告。它校验每题提交的原始 query、Top 5 参数、完整 MCP 结果结构、问题和预测 ID、证据充分性与拒答规则，并要求引用文件、页码和 chunk ID 与检索结果一致。

该模式保存的是子 agent 提交并经 Runner 校验的 MCP 结果，不是 Codex 宿主捕获的原始 JSONL 工具事件；因此它能验证结构和内部一致性，但不能像旧的嵌套 CLI 原型一样独立证明真实工具调用次数。`manifest.json` 通过 `trace_provenance=subagent-submitted-mcp-result` 明确记录这一边界。

## 五、答案评估器扩展

`evaluation/evaluate_answers.py` 已扩展以下指标：

- 答案事实覆盖诊断；
- 人工正确率和完整性；
- 引用准确率与引用召回率；
- 答案是否具有受支持引用；
- 引用的文件、页码和 chunk ID 是否完整；
- 错误回答率；
- 错误拒答率；
- `evidence_sufficient=false` 时的拒答遵守率；
- 使用模型记忆或猜测的比例。

人工复核字段固定为：

```json
{
  "correct": null,
  "complete": null,
  "citation_supported": null,
  "uses_model_memory_or_guess": null
}
```

自动字符匹配只作为诊断，最终正确性、完整性和引用支持结论以人工复核为准。

### 失败归因

报告为每题给出一个主要阶段：

| 阶段 | 判定方式 |
| --- | --- |
| `retrieval_error` | 可回答问题的 Top 5 中没有人工标注的相关 chunk |
| `evidence_judgment_error` | 已检索到相关 chunk 却判断证据不足，或不可回答问题被判断为证据充分 |
| `generation_error` | 客户端违反拒答要求、错误拒答、漏引相关证据，或人工复核发现错误、不完整、无证据支持或使用模型记忆 |
| `pending_manual_review` | 检索、证据判断和引用初检通过，等待人工复核 |
| `passed` | 所有自动检查和人工复核均通过 |

因此报告能够区分检索错误、证据判断错误和生成错误，不再只提供一个总分。

## 八、当前状态与后续动作

正式运行会把 12 个问题以及每题最多 5 条 MCP 检索到的本地校园 PDF 证据片段发送给当前 Codex 服务。Skill 会在运行前明确告知这一外发范围；当前固定数据集只引用仓库中已批准用于评测的两份公开输入。

当前 `evaluation/release_manifest.json` 属于第一优先级开始前的冻结周期。`README.md`、`evaluation/evaluate_answers.py`、`src/mcp_server.py` 和相关测试已经进入新的代码基线，用该历史清单校验当前源码会出现预期的哈希/大小差异。本次不覆盖历史清单，也不把它描述成当前第一优先级的冻结结果；是否创建新发布清单应在真实评测状态确定后另行处理。

同理，现有 `evaluation/reproduction_plan.json` 的 `unit-tests` 步骤仍运行上一周期的 `unittest discover`，不会收集当前全部 pytest 风格测试。本报告的 100 项结果来自单独执行的当前完整 pytest 套件；本次不修改历史复现计划，以免在第一优先级未完成时提前进入第二优先级收口。

此外，`docs/` 已纳入版本控制，当前报告会进入提交并随分支传递；`slides/` 仍被 Git 忽略，不包含在本次提交中。

执行真实评测时，仅继续第一优先级，按以下顺序完成：

1. 使用 `$rag-answer-evaluation` 准备任务，并以逐题全新子 agent 生成 12 个结果文件；
2. 运行 Runner 校验、汇总并生成真实预测；
3. 逐题人工复核正确性、完整性、引用支持和模型记忆使用情况；
4. 重新运行答案评估器生成带人工复核的最终报告；
5. 将真实指标和失败案例补充到本报告，不开展第二及以后优先级工作。

在正式运行前，不声明答案正确率、引用准确率或拒答遵守率已经达到验收标准。
